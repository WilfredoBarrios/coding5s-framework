# 🤝 Contributing to Coding5s

First off, thank you for taking the time to contribute! It is developers, educators, and language stewards like you who make Coding5s an impactful framework for breaking Tutorial Hell worldwide.

By contributing to this project, you agree to abide by our [Code of Conduct](CODE_OF_CONDUCT.md) and that your contributions will be licensed under the [MIT License](LICENSE).

---

## 🚀 Getting Started

1. Fork the repository
2. Clone your fork: `git clone https://github.com/YOUR-USERNAME/coding5s.git`
3. Create a branch: `git checkout -b feature/your-feature-name`
4. Make your changes
5. Commit: `git commit -m 'Add some feature'`
6. Push: `git push origin feature/your-feature-name`
7. Open a Pull Request

---

## 🗺️ Where Can You Contribute?

The Coding5s ecosystem is multi-disciplinary. You don't need to be a senior software engineer to contribute. We actively seek help in the following areas:

1. **Curriculum Design (Pillar 1 & Pillar 3):** Helping expand the spreadsheets or datasets to support new programming languages, framework stacks, or infrastructure labs.
2. **Prompt Engineering & Testing (Pillar 2):** Stress-testing our Socratic Swarm Mentors across different LLMs (local vs. cloud) to ensure strict compliance with our pedagogical constraints.
3. **Localization & Language Seeds (Core Frontier):** Translating and validating our semantic technology matrices into global and regional languages—with a high-priority focus on indigenous languages such as **Q'eqchi'** and **Kaqchikel**.

## 📝 Style Guide

### Documentation
- Use Markdown for all documentation files
- Keep sentences clear and concise
- Use code blocks for prompts, formulas, and technical examples
- Include examples whenever possible

### Prompts & Formulas
- Follow the ECP (Ephemeral Context Protocol) syntax for state management
- Use the Firmware dictionary defined in `/engine/firmware.md`
- Test your prompts with at least 2 different LLMs before submitting

## 🌐 Our Pull Request Process

To ensure structural consistency across the framework, please follow these steps before submitting a Pull Request (PR):

### 1. Check for Existing Issues
Before writing any code or updating any documentation, check the GitHub Issue Tracker to make sure someone else isn't already working on the same thing. If no issue exists, please open a new one to discuss your proposal.

### 2. Branch Naming Conventions
Create a descriptive branch name from `main` using our structural prefixes:
- `feature/` -> For adding new modules, domains, or languages.
- `fix/` -> For fixing prompt bugs, typos, or formula errors.
- `docs/` -> For updates to methodologies, guides, or READMEs.
- `experimental/` -> For testing new context optimization theories (e.g., ECP/DSL).

*Example:* `feature/localization-qeqchi-seed`

### 3. Maintain Matrix Integrity
If you are modifying the Creator Kits (`/formulas/` or `/examples/`), verify that your structural additions do not break the strict cascading formulas or exceed character limits per cell.

### 4. Format Your PR Documentation
When opening a PR, clearly describe:
- The core problem or feature.
- The specific pillars or documentation files altered.
- Any empirical testing data (e.g., how an LLM responded to your prompt modifications).

## 🌍 Special Focus: Language Seed Contributions

Our localization pipeline relies on `LANGUAGE_SEED_CONTEXT.md` and `GENERAL_SEED_CONTEXT.md`. If you are contributing to a regional or indigenous language:
- Do not perform raw machine translation. Every token must maintain strict pedagogical value.
- Ensure technical definitions are mapped accurately so that the Socratic Mentors can guide students without semantic degradation.
- Coordinate directly with native speakers or linguistic researchers whenever possible.

---

## 🐛 Reporting Bugs & Prompt Failures

If you discover a scenario where an AI Mentor breaks its Socratic contract (e.g., it writes raw code for a user instead of asking questions), please open a Bug Report issue and include:
1. The target technology and lesson stage (`STAGE 1-5`).
2. The core model and provider used (e.g., Ollama/Llama-3-8B, GPT-4o).
3. The exact raw prompt payload generated by the spreadsheet that caused the failure. 
(Note: The results depend directly on the LLM used. Premium LLMs give better results.)
